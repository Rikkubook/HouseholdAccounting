# 需求訪談紀錄（2026-10）

SA 訪談使用者的完整過程，保留每一題的問法、回答、推導與訪談技巧，可當作日後訪談他人的範例。結論見 [README.md](README.md)；文中的 R、G、ST、O 等編號說明見 README 的「編號說明」。

## 0. 訪談架構

| 層次 | 問什麼 | 本次 |
|---|---|---|
| 1. 人與目的 | 誰在用、最想回答什麼問題 | 第 0 輪 |
| 2. 使用情境 | 每天記帳、月中查看、年度回顧、設定維護 | 情境 ① 一輪 |
| 3. 倒推功能 | 從目的倒推分類、預算、訂閱…… | 第 2 輪 Q1～Q17 |
| 4. 對照現況 | 推導結果與現有 App 逐項比對 | 每題當下＋最後總表 |

原本規劃逐頁訪談（先資料來源頁，後報表頁），實際上跟著回答追問而偏離，後來改成「情境為主、頁面為輔」，再改為「從目的倒推」。三種方式的優缺點見第 5 節。

## 1. 第 0 輪：人與目的

| 題目 | 回答 | 推導 |
|---|---|---|
| 實際上誰在用？ | 2 人；10 月才開始，9 月前用系統匯入；可以代記 | 使用者數、資料起點 |
| 另一位是什麼角色？ | 兩位都是管理者 | 一般成員權限不必細談 |
| 打開 App 最想看到什麼？ | A（本月預算）＞ C（每人花費）＞ B（年度結餘），但都需要 | 功能優先序 |
| 「每人花多少」是什麼用途？ | 每月算共用金給付時，依此人花費計算 | 發現隱藏需求：共用金結算 |
| 請用 9 月實際例子走一遍 | A 花 15,000、B 花 20,000；共用金浮動要能輸入；給 A 15,000、B 20,000，餘額 N | 結算公式 |
| 餘額 N 怎麼處理？ | 滾到下個月 | |
| 每人花費算哪些交易？ | 代記算我選的人；建議的 6 項都對 | 花費口徑 |
| 結算後回頭改帳怎麼辦？（鎖帳／自動調整／不追溯） | 太複雜 | 退一步改為即時計算 |
| — | 從頭來，我想一下；共用金先拿掉 | 共用金結算移出範圍 |
| 每人花費 | 要算本月的每人花費 | 只看當月 |
| 放在哪一頁？ | 統計圖表頁 | |
| 呈現方式？ | 卡片＋圓餅圖 | |
| 年度切換時？ | 統計表不用年度，年度看年度彙整 | 統計頁移除年度 |
| 成員篩選？ | 不用 | 統計頁移除成員篩選 |
| 固定支出用訂閱設定還是實際交易？ | 維持現狀 | 記錄後果：總額不一致是設計如此 |

**技巧**

- **先問人和目的，再問功能**：目的決定取捨。
- **逼對方排優先序**：對方幾乎都會說「都要」，排序才看得出資源先放哪。
- **追問「為什麼要」**：表面需求（看每人數字）後面是真需求（算錢）。
- **請對方舉真實例子**：數字例子比抽象描述更快對齊。
- **複述確認**：用自己的話說一次，對方才發現哪裡不對。
- **對方說太複雜就退一步**：需求要配合對方能承受的複雜度。
- **說清楚決定的後果**：避免日後被當成 bug 回報。

**失誤**：一次丟出 6 項表格請對方逐項回覆，對方只回了 1 項，要再問一次。一次只問一件事反而更快。

## 2. 情境 ① 日常記帳

| 題目 | 回答 | 推導 |
|---|---|---|
| 描述你最近一次記帳的過程 | 「我需要記錄晚餐－義大利麵 400」 | 回答的是內容不是過程；欄位現況都有 |
| 通常什麼時候記？ | 不一定 | 三種時機都要顧 |
| 哪一種最麻煩？ | （跳過） | 記為未知 |
| 上次代記是什麼情況？ | （跳過，要求看推導結果） | — |

**推導結果**：設計「不改」，另列觀察項 O-01～O-04（見 README 第 7 節）。

**技巧**

- **情境重現**：問「最近一次怎麼做」，不問「你需要什麼功能」。
- **接住內容再換角度**：對方答非所問時不糾正，先對到系統上，再問更具體的題目。
- **「不一定」改問「哪個最痛」**：痛點比頻率好回答。
- **跳過就照預設往下走**：硬逼只會得到編出來的答案。
- **推導要標示把握程度**：對方明說的和從沉默推論的，可靠度不同。
- **不要發明需求**：SA 看到的「可以更好」，對方沒抱怨就只是觀察項。
- **用資料驗證**：上線後的使用紀錄比回想可靠。

**反省**：把「跳過」推論成「沒有痛點」太弱，應標記「未知」，再用觀察或資料驗證。

## 3. 應付簡短回答

使用者指出：真實的受訪者也會像這樣簡短回答。回頭看本次的回答模式：

| 問法 | 回答 |
|---|---|
| 開放題 | 最短，或跳過 |
| 給選項 | 一個字母 |
| 給具體方案讓對方挑錯 | 最有資訊量（「統計不用年度」「成員也不用」「太複雜了」） |

對策：

1. **讓對方反應，不要讓對方生答案**：給畫面、例子、方案。
2. **看他做，不要聽他說**：請對方當場操作一次，觀察卡在哪。
3. **先講預設，讓對方行使否決權**：「我打算這樣做，不同意再說」。
4. **題目短、一次一件事**。
5. **簡短不等於沒需求**：標記未知，另外驗證。

### 觀察的盲點：問不出結構性需求

「看他做」只能看到現有工具怎麼用，問不出「為什麼需要分類」。三個方法：

| 方法 | 問出什麼 | 時機 |
|---|---|---|
| 從「記完要拿來做什麼」倒推 | 為什麼需要這個欄位 | 從零開始的訪談 |
| 看對方現在用的東西（試算表、發票） | 已經在做的結構 | 訪談前準備 |
| 聽用詞（「晚餐－義大利麵 400」本身就是 分類－備註 金額） | 腦中的結構 | 每一個回答 |
| 看他操作 | 現有系統哪裡不順 | 系統已存在時 |

> 不要問使用者要什麼功能，要問他想回答什麼問題，功能由 SA 推導。

## 5. 三種訪談架構的比較（本次實際走過）

| 架構 | 優點 | 缺點 | 適用 |
|---|---|---|---|
| 逐頁 | 有結構、不漏頁 | 跨頁需求（如共用金結算）可能永遠不會被問到 | 系統已存在、做驗收 |
| 跟著回答追問 | 能抓到真正的核心 | 跳來跳去，受訪者不知道進度 | 探索期 |
| 從目的倒推 | 問得出結構性需求，題目短 | 需要先知道目的 | 從零開始、或重新驗證現有系統 |

本次最有效的組合：**第 0 輪問目的 → 倒推功能 → 每題當下對照現況 → 最後總表**。
