# 需求釐清結果（2026-10 訪談）

由 SA 訪談使用者（家中管理者）所得。訪談過程、每一題的推導與訪談技巧見 [interview-log.md](interview-log.md)。

- 訪談日期：2026-10-07～10-08
- 對照版本：v1.5.1（`main`）；2026-10-12 依 v1.5.2 重新核對
- 方法：先問使用者與目的，再從「想回答的問題」倒推功能，最後與現有 App 逐項對照

## 編號說明

| 前綴 | 全稱 | 意思 | 範例 |
|---|---|---|---|
| R | Requirement（需求） | 從訪談推導出、使用者確認過的需求，不管現有 App 有沒有做到 | R-04 每個分類有月預算 |
| G | Gap（缺口） | 需求和現有 App 不一致、需要修改的地方。一個 G 通常對應一到多個 R | G-1 刪除前要確認 |
| ST | Stats（統計圖表頁） | G-4 統計圖表頁改版的細部規格 | ST-02 移除成員篩選 |
| G6 | G-6 的細部規格 | G-6 年繳訂閱拆月交易的細部規則 | G6-04 餘數放最後一筆 |
| O | Observation（觀察項） | SA 看程式發現可能不便、但使用者沒有反映的地方。**不是需求**，等有資料驗證後再決定要不要轉成 R | O-02 存檔後不停留連續記帳 |

關係：**R（要什麼）→ 與現況比對 → G（要改什麼）→ ST／G6（怎麼改）**。O 不在這條線上，是待驗證的假設。

## 0. 摘要

- 現有 App 大致符合需求：推導出的 10 項核心需求已有對應功能（第 2 節）
- 缺口 6 項，其中 1 項為大改（年繳訂閱拆月交易，G-6），1 項不需改程式（新增「獎金」分類，G-5）；G-4 已於 v1.5.2 完成
- 不做：共用金結算（暫緩）、個人帳（以後再說）
- changelog-2026-10-07「待決定」4 項中已決定 3 項（第 5 節）

## 4. 定案規格

### 4.1 統計圖表頁（G-4）

| 編號 | 需求 |
|---|---|
| ST-01 | 只提供月份檢視，移除「月份／年度」切換；年度數字一律看年度彙整頁 |
| ST-02 | 移除成員篩選 |
| ST-03 | 新增「當月支出比例」卡片，以橫向比例條呈現所選月份每位成員的支出金額與佔比；各段用成員自選顏色，下方標示名稱、金額、百分比（v1.5.2 實作，原訂圓餅圖，使用者改為比例條） |
| ST-04 | 比例條口徑：算記帳者（代記算所選的人）；訂閱交易算扣款人；不含收入、年度額外開銷 |
| ST-05 | 不屬於任何啟用成員的支出（「系統」匯入、已停用成員）併成灰色「其他」段，排在最後（v1.5.2 實作，使用者確認）；花費為 0 的成員不顯示（使用者確認）；當月完全沒有支出時顯示「這個月還沒有支出」 |
| ST-06 | 「浮動支出 · 實際 vs 預計」維持現狀 |
| ST-07 | 固定支出清單維持以訂閱設定換算；說明文字維持「不另做圖，僅清單呈現」（使用者確認） |
| ST-08 | 本頁總額不要求與年度彙整一致（設計如此） |


### 4.2 年繳訂閱拆月交易（G-6）

| 編號 | 需求 |
|---|---|
| G6-01 | 年繳不記一筆總額，改為每月產生一筆分攤交易 |
| G6-02 | 自扣款月起算 12 個月（例：2026-10-05 年繳 6,000 → 2026-10～2027-09 每月 500） |
| G6-03 | 每月到期當天產生一筆，日期與扣款日同日；不預先產生未來的交易 |
| G6-04 | 每筆＝年費 ÷ 12 取整數，餘數放在最後一筆，12 筆合計等於年費 |
| G6-05 | 中途停用：已付期間繼續產生到期滿 |
| G6-06 | 中途調整金額：本期照舊金額拆完，下一期才用新金額 |
| G6-07 | 記帳者＝訂閱的扣款人 |
| G6-08 | ~~訂閱頁「標記已扣款」對年繳同樣改為產生當月分攤交易~~ → 2026-10-14 使用者決定拿掉「標記已扣款」按鈕，一律由每日自動扣款產生（後端 API 保留，供排程失敗時補扣） |
| G6-09 | 訂閱頁年繳的「下次扣款日」顯示下次實際年繳日（含年份），旁邊標「分攤 n/12」（2026-10-14 開發前確認） |
| G6-10 | 分攤進行中（第 2～12 期）不能改週期與扣款日，編輯視窗鎖住並說明；改金額從下一期起生效（開發時補充，2026-10-14 使用者確認） |
| G6-11 | 「今天」一律以台灣時間判斷（前後端都是）：每日自動扣款在台灣凌晨 2 點執行時就產生當天的交易，不再晚一天；新增交易的預設日期在台灣凌晨也不會變成前一天（2026-10-14 使用者決定） |

既有資料：正式庫沒有年繳訂閱（2026-10-14 使用者確認），不需轉換既有的整筆年費交易。

已知後果（使用者已接受）：

- 交易列表看不到實際扣款的總額，與銀行／信用卡帳單無法逐筆對帳
- 現有分攤邏輯（`api/src/services/fixed.ts`，自扣款月起算、停用後攤到期滿）規則相同，可沿用

## 6. 不做／暫緩

| 項目 | 說明 |
|---|---|
| 共用金結算 | 原需求：每月手動輸入共用金，依每人當月花費撥還，餘額（含負數）滾到下月。使用者覺得結算後改帳的處理太複雜，先拿掉。若重啟，已確認的口徑：算記帳者、訂閱算扣款人，不含收入、年度額外開銷、系統匯入資料 |
| 個人帳 | 以後可能需要。重啟前先 revert `4b78361`（見該 commit 說明） |
| 交易還原 | 不需要；維持軟刪除，前台不提供還原 |
| 超支主動提醒 | 不需要；變紅即可 |
