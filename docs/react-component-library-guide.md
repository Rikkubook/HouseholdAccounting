# React 專案的元件庫規劃（配合 Claude Design）

## 目的

把元件庫做成**獨立套件**，帶來兩個好處：

1. 可以用 Claude Code 的 `/design-sync` 同步到 Claude Design，讓設計 AI 直接用我們真的元件設計畫面，設計稿可以 1:1 對應到程式
2. 同一套元件可以給其他專案共用

## `/design-sync` 的使用條件

| 條件 | 說明 |
|---|---|
| **React 元件庫** | 必要。Claude Design 用 React 繪製畫面，Vue、Angular 無法使用 |
| **獨立套件，能單獨打包出 `dist/`** | 必要。它打包的是元件庫的成品，元件放在 App 裡面就沒辦法單獨打包 |
| 登入 claude.ai | 必要。要有權限建立、寫入 Claude Design 的專案 |
| Storybook | 選用。有的話同步時會拿它當標準答案比對，見下方「要不要做 Storybook」 |

## 開專案時先做好的事

這幾件事**一開始做很簡單，事後補很痛苦**：

| # | 做法 | 必要性 | 為什麼 |
|---|---|:-:|---|
| 1 | 元件庫獨立成一個套件（`packages/ui/`），不要放在 App 的 `src/components/` | 必要 | 才能單獨打包出 `dist/` |
| 2 | 顏色、字級、間距做成 CSS 變數（例如 `tokens.css`） | 必要 | 設計 AI 會照變數名稱用顏色；寫死色碼它只能用猜的 |
| 3 | 元件的 props 用 TypeScript 定義 | 必要 | 會自動產生每個元件的參數說明書給設計 AI |
| 4 | 元件需要包 Provider（主題、語系）的話，寫在文件裡 | 必要 | 設計 AI 不知道要包，畫出來就沒有樣式 |
| 5 | 基本元件寫 Storybook story | 選用 | 同步時當作比對的標準答案；見下方說明 |

## 要不要做 Storybook

**可以不做。** 沒有 Storybook，元件一樣能同步、AI 一樣能使用。差別在同步時的檢查：

| | 有 Storybook | 沒有 Storybook |
|---|---|---|
| 元件能不能同步、讓 AI 使用 | ✅ 可以 | ✅ 一樣可以 |
| 同步時怎麼檢查畫得對不對 | 拿 Storybook 的畫面當**標準答案**逐一比對 | 沒有標準答案，依通用標準評分 |
| 元件預覽卡 | 每個元件都有完整預覽 | 只有**指定的元件**有完整預覽，其他是陽春版 |

Storybook 在這裡的讀者是**同步工具，不是人**。「沒人會看」不是判斷依據，要看的是元件的數量和複雜度：

| 情況 | 建議 |
|---|---|
| 元件少（約 20 個以內）、樣式單純 | **不做**，同步後到 Claude Design 人工看一遍預覽卡 |
| 元件多、狀態複雜（hover、停用、錯誤…） | 只幫**基本元件**（按鈕、輸入框、下拉）寫 story，不用全部寫 |

## 建議的資料夾結構

```
my-app/                      ← monorepo（一個 git 倉庫）
├── packages/
│   └── ui/                  ← 元件庫套件（/design-sync 在這裡執行）
│       ├── .storybook/      ← 選用
│       ├── src/
│       │   ├── tokens.css   ← 顏色、字級變數
│       │   └── Button/
│       │       ├── Button.tsx
│       │       └── Button.stories.tsx   ← 選用
│       ├── dist/            ← 打包成品（自動產生，不進 git）
│       └── package.json
├── apps/
│   └── web/                 ← App 本身，引用 packages/ui
├── api/                     ← 後端（如果有）
└── pnpm-workspace.yaml      ← 宣告有哪些套件
```

## 名詞：monorepo 與套件

| 名詞 | 是什麼 | 比喻 |
|---|---|---|
| **monorepo** | 整個大資料夾（一個 git 倉庫），裡面裝好幾個套件 | 一棟大樓 |
| **套件**（package） | 有自己 `package.json` 的子資料夾 | 大樓裡的一間房 |

元件庫是**在 monorepo 裡多隔出來的一間房**（`packages/ui/`），不是另外再開一個 monorepo。

## 其他專案怎麼使用元件庫

| 其他專案在哪 | 做法 |
|---|---|
| **同一個 monorepo 裡**（例如 `apps/admin/`） | 直接在它的 `package.json` 加上依賴，改一次所有 App 同步 |
| **另一個 git 倉庫** | 把 `packages/ui/` 發布到 npm 或 GitHub Packages，對方用 `pnpm add` 安裝；之後靠版本號控制更新 |

## 新專案 vs. 既有專案

**最適合全新專案**；既有的 React 專案也可以做，但要分階段搬。

| 專案狀況 | 適合嗎 | 成本 |
|---|---|---|
| 全新 React 專案 | ✅ 最適合 | 幾乎沒有，照結構開就好 |
| 既有 React 專案，元件寫得乾淨（只靠 props、樣式用 CSS 變數） | ✅ 適合 | 中：搬檔案、改 import 路徑 |
| 既有 React 專案，元件跟 App 綁很緊（直接打 API、讀全域狀態、依賴路由） | 🟡 先整理再搬 | 高：要先把元件跟 App 邏輯拆開 |
| 既有的非 React 專案（Vue、Angular） | ❌ 不適合 | 等於重寫前端；改用人工維護 Design System |

判斷關鍵：**元件能不能單獨拿出來運作。**

### 既有 React 專案的搬法

| 階段 | 做什麼 | 重點 |
|---|---|---|
| 1. 建立空殼 | 新增 `packages/ui/`，在 `pnpm-workspace.yaml` 加一行 | App 先不動，確認能正常建置 |
| 2. 先搬最基本的元件 | 按鈕、輸入框、標籤這類不依賴任何東西的元件 | 搬一個、改一個 import、確認沒壞再搬下一個 |
| 3. 整理顏色 | 寫死的色碼改成 CSS 變數，集中到 `tokens.css` | 可和第 2 階段同時進行 |
| 4. 第一次 `/design-sync` | 只同步已經搬好的元件 | 不用等全部搬完，之後每搬一批再同步一次 |
| 5. 處理綁很緊的元件 | 把「打 API、讀全域狀態」移回 App，元件只留畫面和 props | 最花時間，可以最後做 |

原則：

- **App 隨時都要能正常運作**，每搬一個就確認一次
- **不是所有元件都要搬**：只用在一頁、跟商業邏輯綁很緊的元件留在 App；要搬的是會重複使用的積木

## 建議的進行順序

| 階段 | 要做到哪裡 | 能得到什麼 |
|---|---|---|
| 1. 開專案時 | 元件庫拆成獨立套件 ＋ 上面的必要事項 | 可以用 `/design-sync` |
| 2. 同 monorepo 有第二個 App 時 | 直接引用 `packages/ui/` | 多個 App 共用元件 |
| 3. 另一個倉庫也要用時 | 發布成套件、管理版本號 | 跨倉庫共用 |

原則：**不要為了「可能會用到」提早做**。Storybook、發布、版本管理都有維護成本，等真的有需要再做。
