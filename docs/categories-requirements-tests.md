# 分類設定頁 — 需求檢視與測試案例

對應前端 `vue3/src/views/CategoriesView.vue`、後端 `api/src/routes/categories.ts`。這份文件是「頁面需求 + 測試範圍 + 測試案例」的示範產出，之後其他頁面（訂閱管理、成員管理…）可比照這個格式再寫。

規模：中（單頁 + 主/子分類共 9 支 API，無 Figma 稿件可對照）

## 0. 摘要

- 需求規模：中——單一管理頁面（`CategoriesView.vue`）+ 對應後端 9 支 API，涉及兩層實體（主分類/子分類）與月份存在性判斷，但沒有金流、沒有 Figma 稿件需要比對
- 需求條目數：9（R-01~R-09）　｜　T 群組數：9　｜　測試案例數：34（含 3 則正式比對）
- 最需要先確認的 3 件事：
  1. 主分類新增**沒有查重**（子分類有查重、主分類沒有）是設計如此還是遺漏？（Q-01，已在程式碼中實際驗證）
  2. 後端已有排序 API（`reorder`），但前端完全沒有串接、沒有任何操作入口——這次要不要一併補上 UI？（Q-02）
  3. 「系統分類」（`isSystem`）的認定範圍是哪些分類？目前只能從種子資料反推，沒有明文規格（Q-03）

## 1. 需求理解與條目

| 編號 | 需求描述（重點） | 類型（明說／隱含） |
|---|---|---|
| R-01 | 管理者可新增主分類：名稱必填（trim 後 1~20 字）、圖示必選、收支類型（支出/收入）、支出須另選浮動/固定，收入不得有性質 | 明說 |
| R-02 | 管理者可編輯主分類名稱與圖示；收支類型與性質建立後不可修改；系統分類不可改名 | 明說 |
| R-03 | 管理者可停用/重新啟用主分類（僅軟刪）；系統分類不可停用；停用寫入 `archivedFrom` = 當月，還原清空該欄位 | 明說 |
| R-04 | 管理者可在指定主分類下新增子分類：名稱必填（1~20字）、同一主分類下不可與既有子分類同名 | 明說 |
| R-05 | 管理者可編輯子分類名稱，同一主分類下不可與「其他」子分類重複（可維持原名） | 明說 |
| R-06 | 管理者可停用/重新啟用子分類（僅軟刪） | 明說 |
| R-07 | 主分類清單可依「全部/浮動支出/固定支出/收入」篩選；停用中的項目排在同一群組最後 | 明說 |
| R-08 | 分類在特定月份是否「存在」需依 `activeFrom`/`archivedFrom` 判斷（`existsInMonth`），供預算與統計等其他頁面計算是否納入 | 隱含（程式碼已實作，規格文字未明寫） |
| R-09 | 主分類、子分類皆有排序 API，理論上應可調整顯示順序 | 隱含（後端已實作，前端未見任何操作入口，範圍待確認） |

## 2. 需求檢視結果

### 2.1 缺漏與不明確處

| 編號 | 面向 | 問題描述 | 建議處理 |
|---|---|---|---|
| G-01 | 資料規則一致性 | `POST /api/categories`（新增主分類）沒有查重邏輯；但子分類新增（`POST /:id/subs`）與改名（`PATCH /subs/:subId`）都有 `conflict("此...名稱已存在")` 檢查。實測可以建出兩個名稱完全相同的主分類 | 與 PM/後端確認是否為刻意設計（例如允許同名但不同收支類型），否則補上查重 |
| G-02 | 功能完整性 | `api/src/routes/categories.ts` 有 `POST /reorder`、`POST /:id/subs/reorder`，`vue3/src/api/categories.ts` 也定義了呼叫方法，但 `stores/categories.ts` 與 `CategoriesView.vue` 完全沒有呼叫過這兩支，畫面上也沒有拖曳/上移下移的操作元件 | 確認這次需求範圍是否包含補上排序 UI，或明確排除、留給下一期 |
| G-03 | 驗收條件 | 停用/還原主分類與子分類都是點擊圖示後直接呼叫 API，沒有二次確認對話框 | 確認「停用」這種可逆但會立即影響其他頁面（交易新增下拉消失）的操作，是否需要確認彈窗 |
| G-04 | 資料規則 | 名稱欄位只限制 trim 後 1~20 字，沒有排除 emoji、特殊符號、純空白全形字元等 | 確認是否要限制可輸入字元集，或維持現狀（多數記帳 App 允許 emoji 當分類名稱屬合理設計） |
| G-05 | 角色與權限 | 「系統分類」（`isSystem`）的認定名單只能從 seed 資料反推，規格文件沒有列出哪些分類是系統保留、為何保留 | 請 PM/後端列出系統分類清單與保留原因，供測試案例對照 |
| G-06 | 資料規則 | 收入類主分類是否該允許子分類？程式碼未排除（`POST /:id/subs` 沒有檢查 `type`），UI「新增子分類」按鈕只排除 `isSystem`、沒有排除收入類 | 確認是否為預期行為 |
| G-07 | UI/UX | 主分類清單本身沒有「無資料」空狀態設計（因為一定有系統分類撐著理論上不會空）；子分類有 `EmptyState`。若篩選條件（例如「收入」）剛好篩出 0 筆主分類，畫面呈現需求未定義 | 確認篩選後 0 筆結果的畫面表現 |

## 3. 測試範圍

### 3.1 範圍內（In Scope）

- **A. 功能面**：主分類/子分類的新增、改名、停用、還原；篩選切換；選取不同主分類後子分類清單連動
- **B. 資料面**：名稱邊界值（0/1/20/21 字）、空白字串、emoji/特殊字元、`type`×`nature` 的合法/不合法組合、月份邊界（`activeFrom`/`archivedFrom` 前後一個月）
- **C. 權限與角色**：一般成員唯讀、寫入操作 403；未登入 401；直接呼叫 API 的越權測試
- **D. UI/UX**：停用樣式（灰階、badge）、Dialog 開關、RWD（手機 chip 呈現 vs 桌面右側子分類卡片）
- **E. 前端（Vue3）**：表單型別聯集（`MainForm`/`SubForm`）綁定、`selectedId` 預設值與篩選連動後的失效情境、`onMounted` 載入時機
- **F. API 串接**：各端點的 2xx/400/401/403/404/409 情境
- **H. 回歸影響範圍**：見 3.3

### 3.2 範圍外（Out of Scope）與理由

- **拖曳排序的實際互動測試**——前端未實作操作入口（G-02），待 Q-02 確認範圍後再補
- **Figma 視覺稿逐項比對**——本次無稿件提供
- **`IconPicker` 圖示庫本身的搜尋/捲動效能**——視為獨立共用元件，非本頁專屬需求

### 3.3 回歸影響範圍

| 受影響項目 | 影響原因 | 建議回歸深度 |
|---|---|---|
| `TransactionCreateView`（新增交易） | 分類停用後應立即從新增交易的分類下拉消失 | 完整：停用後立刻驗證下拉選單 |
| `BudgetView`（預算管理） | 僅浮動支出分類可設預算；分類名稱變更、停用/還原、`existsInMonth` 判斷都直接影響此頁 | 完整 |
| `DashboardView`（首頁儀表板） | 分類進度條依浮動支出分類與其預算計算 | 抽測：改名、停用各驗證一次 |
| `StatsView` / `YearSummaryView` | 統計依分類分組；歷史交易保留分類名稱快照，不受改名影響 | 抽測：驗證「改名後歷史交易仍顯示舊快照名稱」這條規則沒被破壞 |

| A-01 | 假設「系統分類」是指種子資料中預先建立、不可刪改的基礎分類（如收入類的「薪資」） | 若實際定義不同，T02-2、T03-3、T04-4 的判定依據需整組重寫 |
| A-02 | 假設子分類的查重邏輯（同主分類內不可重名）是刻意設計，主分類沒有查重是遺漏而非刻意 | 若主分類真的允許同名是刻意設計，T01-7 需從「疑似缺陷」改為「預期行為」 |
| A-03 | 假設本頁僅 ADMIN 可進入，一般成員完全看不到此頁面入口（依路由 `meta.admin` 推斷） | 若一般成員應可唯讀進入，T08-1 需整條重寫並補上唯讀情境案例 |

### 6.3 高風險項目與建議測試順序

1. **T01-7（主分類查重）**——風險最高，因為已用程式碼證實現況會建出重複分類，建議第一個確認，結果會影響是否需要開一張後端修復單
2. **T10（月份存在性判斷）**——牽動預算、統計、年度彙整等多個下游頁面，建議在 T01~T06 基本 CRUD 確認無誤後，優先驗證
3. **T08（權限）**——涉及資料安全，建議排在 T01~T06 之後、T09 之前執行
4. 其餘 T02~T07、T09 可依開發完成順序穿插執行
